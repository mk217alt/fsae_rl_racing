01 How the training actually works

Car 2 learns by trial and error, not by copying Car 1's human driving. Every physics step, it looks at where it is relative to the track centerline, picks a throttle/steer action, and gets scored on how well that worked. Repeat that a few hundred thousand times and a driving policy falls out.

02 Every mistake, in order

Nothing here worked on the first try. Kept in order because the fixes build on each other — including the two phases before the car project even existed.

Phase 1 — Isaac Sim itself

The simulator wouldn't even start

Before any of this existed, Isaac Sim 5.1.0 crashed on every launch inside its RTX renderer (rtx.scenedb.plugin.dll), consistently, within the first few seconds.

Mistake

Assumed it was this laptop's hybrid NVIDIA/AMD graphics fighting each other, and spent real effort ruling that out — disabling third-party Vulkan overlay layers (Steam, Discord, GeForce Experience) one by one, then restricting the Vulkan loader to only the NVIDIA ICD via VK_ICD_FILENAMES so the AMD GPU couldn't be involved at all. The crash persisted through every one of those tests.

Fix

The real cause was simpler: the newest GPU driver branch (610.x) is unvalidated for this Isaac Sim build. Rolled back to driver 580.88, the officially validated version — confirmed against the exact crash signature in public Isaac Sim issue trackers. A second, unrelated Code 43 GPU error surfaced right after that install, traced to a power-management setting and a conflicting Windows Update driver push.

Phase 2 — Isaac Lab, validating the toolchain

Four dependencies, each broken by fixing the last one

Before committing to the thesis's actual vehicle-racing environment, Isaac Lab was installed and exercised on a stock example task — training a Franka arm to pick up a cube — purely to validate that the RL toolchain (Isaac Lab, rsl_rl, PPO) worked end to end on this machine at all, independent of any project-specific code.

Mistake

Installed the main branch first, which requires Python 3.12 — but Isaac Sim 5.1.0 ships Python 3.11. Switched to the matching v2.3.2 release tag, which then hit a chain of its own: a pinned dependency (flatdict) failed to build because its isolated build environment couldn't find pkg_resources; installing it manually pulled in a newer tensordict that crashed on import with a native access violation (an ABI mismatch against the pinned torch version); downgrading tensordict to match dragged numpy to a version Isaac Lab explicitly forbids; fixing numpy broke h5py the same way.

Fix

Each link was pinned to the exact version compatible with the one before it (flatdict==4.0.1 built with --no-build-isolation, tensordict==0.7.2, numpy<2, h5py==3.12.1) until the whole chain held together. Validated the entire pipeline by training a Franka arm lift-cube task with rsl_rl PPO — real learning, confirmed end to end. With the toolchain proven, the actual thesis work — the car, the track, and an RL policy learning to race it — followed directly.

Phase 3 — building the car

Decorations warped by their own parent's scale

A Formula-style body kit (nose cone, sidepods, wheel arches) was attached under the chassis rigid body.

Mistake

The chassis was a scaled Cube acting as both the collision shape and the rigid body. Every decoration parented under it silently inherited that same non-uniform scale, stretching and mispositioning every piece.

Fix

Rebuilt the chassis as a plain Xform "link" with the sized Cube as a child collision shape — the standard PhysX authoring pattern. This fixed the scale bug outright, but exposed a second, deeper problem next.

Phase 4 — building the car

A duplicate car that wouldn't go away

Even after the scale fix, a frozen "ghost" copy of the decorated car rendered alongside the live, driving one.

Mistake

Diagnostic scripts confirmed the saved USD file only ever contained one car hierarchy — so this wasn't a data bug. It was traced to Isaac Sim's Fabric simulation cache and the regular USD render delegate drawing the same rigid body from two different sources at once. Forcing /physics/updateToUsd and disabling the Fabric scene delegate didn't resolve it.

Fix

Removed the decorative body kit entirely and kept the plain functional car, which had always rendered correctly. The open question — nested cosmetic geometry under a simulated rigid body — is parked for a future attempt (single baked mesh, most likely).

Phase 5 — building the track

Corners landed 224 meters away

The rounded-square track is built by placing thin box segments along a computed polyline, each scaled, rotated, and translated into place.

Mistake

USD composes transform operations in the reverse of the order they're added — the last op added acts on the geometry first. Adding Scale → Rotate → Translate actually executed as Translate → Rotate → Scale, so every segment's position was itself getting rotated and scaled before placement.

Fix

Proved it with a two-line isolated test (translate (10,0,0), rotate 45°, scale (2,1,0.4) → read back — got (14.14, 7.07, 0), exactly what reversed composition predicts). Reordered every call site to Translate → Rotate → Scale, then added a standing verify_track.py that reads back world positions before any new track geometry is trusted.

Phase 6 — the RL environment

Driving forward paid a penalty

First smoke test: constant forward throttle, straight wheels — and the reward got steadily more negative as the car sped up.

Mistake

The reset logic pointed the car 180° opposite the track polyline's own direction of travel, reasoning that applied to only one specific spawn segment but was applied everywhere. "Forward" in the car's own frame corresponded to decreasing progress along the track.

Fix

Dropped the extra 180° flip so the car's nose matches the polyline's own direction at every segment. Re-ran the same smoke test: reward now rises cleanly from 0.004 to 0.18 as speed builds — confirmed before any real training was ever launched.

Phase 7 — training iterations

Coin-flip reliability at 50k steps

The first full training run showed real learning, but roughly half of all episodes still ended in a crash off-track.

Mistake

N/A — this was the reward function doing exactly what it was told to; centering and off-track penalties simply weren't weighted heavily enough yet to dominate the policy's behavior.

Fix

Reprioritized explicitly: stay centered first, accelerate second. Raised the centering penalty and off-track penalty, added a dedicated throttle bonus, and kept training from the same checkpoint rather than starting over. By 150k cumulative steps, the last 25+ episodes were all full-length with steady reward in the 46–63 range.

Phase 8 — going in circles, briefly

Stuck for two minutes, then fine

The first live demo of the 150k-step policy was watched only through a periodic position-telemetry log — this session has no way to see the rendered Isaac Sim window directly.

Mistake

Telemetry showed Car 2 barely creeping (about 0.16 m of net movement) for roughly 140 seconds of sim time, right after the auto-recovery teleport fired twice in quick succession — consistent with being physically wedged against a curb, though not conclusively diagnosed.

Fix

Not yet isolated at the time — it recovered on its own and drove smoothly for the rest of the ~15-minute session. See §5 for how this resolved with later policies.

Phase 9 — editing a running process

Changing the reward mid-flight did nothing

Asked to push the reward weights even higher while a training run was already in progress.

Mistake

Python had already read the old constants into memory when the training process started; editing the source file on disk has no effect on a process already running.

Fix

Stopped the in-flight run, accepted the loss of its unsaved partial progress (checkpoints are only written at the very end of each invocation, not incrementally), and restarted from the last saved 150k checkpoint with the new weights.

03 The behavioral-cloning experiment — a negative result

With Run 5's pure-RL policy converged, the next idea was to make Car 2 drive more like its human-driven counterpart: record actual driving, pretrain the policy network on it, then let PPO fine-tune from that starting point instead of from scratch — hoping for a policy that both converges faster and drives in a recognizably human style. It didn't work, across three full rounds and five separate fixes, and the reason it didn't work turned out to be more interesting than any of the individual bugs.

Round 1, setup

Recording a human baseline

record_driving.py drove Car 1 by keyboard for several laps, sampling (observation, action) pairs at the same decision cadence the RL environment trains at (every 4 physics steps) — 2,608 samples in total. pretrain_bc.py then fit Car 2's policy network to reproduce those actions via supervised MSE regression, no simulator needed for this step. Training loss converged smoothly from 0.197 to about 0.041 over 300 epochs.

Round 1, attempt 1 — direct fine-tune

A well-fit mean, buried in noise

Handed the BC-pretrained policy straight to PPO for 50k timesteps of fine-tuning.

Mistake

BC only regressed the policy's action mean. Its action-noise parameter (log_std) was left at stable-baselines3's default of 0.0 — a standard deviation of 1.0, enormous next to a [−1, 1] action range. Every rollout PPO actually collected sampled almost pure noise instead of the well-fit mean: episode length collapsed from 137 to 81 steps over the run and reward never rose above −37.

Fix

Tightened log_std to a standard deviation of 0.15 before handing the policy to PPO. This fixed the noise problem specifically — but not the underlying outcome, as the next two attempts showed.

Round 1, attempt 2 — warm-start the critic too

Fixing the noise didn't fix the plateau

With sane action noise, reward was still deeply negative and, oddly, episode length kept falling as training went on rather than recovering. Working theory: BC pretraining only ever touched the actor, so the critic (value network) started completely uncalibrated — its early advantage estimates were close to random, and PPO trusted them enough to actively degrade the good BC actor before the critic could catch up.

Mistake

Confirmed by collecting 40 real rollout episodes under the frozen BC actor and regressing the critic alone on their Monte-Carlo returns (warmup_critic.py) — first pass silently failed because env.close() was called before the regression step ran, tearing down the whole Isaac Sim process mid-script.

Fix

Moved env.close() to the end of the script. The warmed critic's loss dropped roughly 13× (4313 → 286 train, 4242 → 323 validation) — genuinely learned to predict real returns. Fine-tuning from this checkpoint no longer showed the sharp degradation, but reward still plateaued: −83 to −117 across every quarter of a 50k-step run, max reward never above −37, and the fraction of full-length episodes actually fell as training went on (13 → 7 comparing the first and last quarter).

Round 1, attempt 3 — slow the updates down

Same ceiling, reached more gently

Hypothesis: the default PPO learning rate (3×10⁻⁴) was simply too large a step for nudging an already-good policy — each update could be knocking the actor back out of the good BC basin about as fast as the critic stabilized it.

Mistake

N/A — this was a reasonable hypothesis, tested cleanly rather than a bug.

Fix

Verified the override actually took effect (PPO.load(..., learning_rate=5e-5), confirmed against the loaded schedule) before committing to a full run, then trained 100k timesteps at 6× lower learning rate. Reward crept up slightly then flatlined at the same ceiling as attempt 2 (−96 → −76, plateauing there), max reward capped at −36, and the full-length episode share shrank again (7% → 4%) over the run.

Round 1, interim verdict

A tempting explanation — driving style

After round 1, the leading theory was that the recorded driving style itself was the problem: the reward function penalizes lateral drift from the centerline heavily (−0.6 × offset every step, plus a hard −30 for leaving the road), and human driving — however competent-looking — might simply hug lines, brake, and countersteer differently than this specific reward rewards. That theory made a clear prediction: driving more deliberately centered the second time around should raise the ceiling. It didn't.

Round 2 — better data, same ceiling

Testing the driving-style theory directly

Re-recorded from scratch (1,841 samples, this time deliberately hugging the centerline) and reran the full pipeline with all three round-1 fixes applied from the start instead of rediscovered one at a time. The early signal looked genuinely promising: sampling the raw BC actor's rollouts (before any RL fine-tuning at all) showed episodes surviving far longer than round 1's data ever produced — 4 of 40 episodes already reached the full 500-step length, versus essentially none before.

Mistake

N/A — the setup was correct; this was a genuine test of the driving-style hypothesis, not a bug hunt.

Fix

None needed — the pipeline ran clean end to end. But 100k timesteps of fine-tuning landed on essentially the identical ceiling as round 1: max reward −37 (round 1's was −36), and the fraction of full-length episodes fell across the run just as before (12% in the first quarter down to under 3% by the last), despite starting from a measurably better-surviving BC actor.

Round 3 — smaller data, same ceiling again

One more independent try, for confidence

A third recording (1,422 samples — smaller than either previous dataset, driven with deliberately varied speed and line rather than one consistent style) ran through the identical pipeline: BC pretrain with log_std already tightened, critic warmup, then 100k timesteps of fine-tuning at the same low learning rate. This wasn't testing a new hypothesis — round 2 had already ruled out driving style — it was a direct replication check on a fully independent dataset before treating the conclusion as settled.

Mistake

N/A — clean run, no bugs.

Fix

None needed. Max reward reached −28.2 — a small edge over rounds 1 and 2 (−36, −37), well within the noise of a stochastic policy, not a meaningfully higher ceiling. The same shape repeated once more: full-length episodes made up 8.5% of the first quarter and fell to 3.7% by the last, reward stayed deeply negative throughout (quartile averages −143 → −93 → −81 → −72).

Verdict

Three datasets, five fixes, one unmoved ceiling

Three independently recorded human driving datasets — natural, deliberately centered, and deliberately varied — of three different sizes (2,608 / 1,841 / 1,422 samples), landed on the same ceiling after five genuinely different fixes (action noise, critic calibration, update step size, plus two clean replications). That rules out both the driving-style theory and a data-volume theory: if either were the real constraint, at least one of three independent attempts should have moved the number, and none of them did. What every round shared instead is the technique — behavioral cloning from a small human dataset, then PPO fine-tuning, against this specific reward and termination boundary. The most likely remaining explanation is that BC pretraining on a small demonstration set gives PPO a confident but narrow starting point — fit tightly to the states the demonstrations happened to visit — while pure RL, having no such basin to begin with, explores broadly from the start and simply needed its own large budget (250k+ steps) to get there rather than a shortcut through imitation.

Decision

Accepted the pure-RL policy (car2_ppo_model.zip, now 450k cumulative steps after Runs 6–7, reward 105–113) as the final result and closed out the BC line of work for good. Three well-motivated, carefully executed rounds that all failed the identical way is about as strong a negative result as this kind of experiment produces — not a stalled investigation, a settled one. It says something specific and citable for the write-up: imitation-learning warm-starts don't help RL here, and it isn't for lack of trying different data or different fixes.

In all three datasets, 100% of the samples have a heading error of more than 90° (mean cos −0.91 to −0.98): Car 1 stands in the scene facing +x, which on its start straight is against the direction of travel of the RL environment, and the track was driven the other way round (left turns, where the RL task needs right turns). 04 Roads not taken

Three real forks, each decided against a stated constraint rather than by default.

Learning method
✓ Chosen — reinforcement learning

Learns purely from trial and error against a reward function. Self-corrects from states it's never seen, at the cost of needing many more environment steps than a supervised approach.

Considered — imitation learning

Record Car 1's human (state, action) pairs and train a supervised model to copy them. Faster to set up and directly uses the human data, but compounds errors on situations the demonstrations never covered — rejected because it can't recover from its own mistakes. (A hybrid — using it only as an RL warm-start, not as the final policy — was tried later anyway, three times, with three different recordings; see §3.)

Training framework
✓ Chosen — custom Gymnasium env

A lightweight environment written directly against the core Isaac Sim Articulation API. Minutes to iterate on, since the car and track are hand-authored USD, not registered Isaac Lab assets.

Considered — Isaac Lab task

The same manager-based framework validated on the Franka arm in Phase 2, with proper task registration and massively parallel environments. More correct for a production task, but registering a new task there is real overhead for a two-car demo track — deferred.

RL library
✓ Chosen — stable-baselines3

A plain gymnasium.Env in, PPO out — the generic single-environment API fit a hand-rolled env with no extra glue code.

Considered — rsl_rl

Already proven on the Franka arm task and faster per-sample at scale, but its runner expects a specialized vectorized-env interface built for thousands of parallel Isaac Lab environments — a mismatch for one car on one track.

05 Parallel training and curvature look-ahead

With the single-env pure-RL policy accepted as final, the next round pushed on two of the "not yet tried" items from §4 at once: speed up training by running many car instances at once, and give the policy a look at the road ahead instead of only its current position.

Architecture

One Isaac Sim process, many clones

True parallel Isaac Sim processes were never an option on this machine — running two kit.exe at once was already known to cause severe resource contention. The actual answer, matching how Isaac Lab itself scales: clone the car+track N times inside one stage, and drive all of them with a single batched Articulation view over a wildcard/list of prim paths. One world.step() call already advances every clone's physics at once, so N cars costs far less than N times the wall-clock — no multiprocessing needed.

Result

Validated first at 6 clones via a smoke test (no crash, curvature values varied correctly per clone), then scaled to 10. Measured throughput: ~152–196 timesteps/second, roughly 2× the original single-env pace (~80/s) — confirmed empirically, not assumed.

Observation change

Seeing the corner before it arrives

Added two dimensions to the observation: sin/cos of the heading change 5 meters ahead along the centerline ("curvature look-ahead"), so the policy can anticipate a turn rather than only react to its current lateral offset. Observation grew from 5 to 7 dimensions — a different input shape than the accepted single-env policy, so this is necessarily a fresh network, not a continuation.

Training results

A higher ceiling, less consistently reached

Across 6→10-clone runs totalling 470k steps, peak reward reached 118.9, later 121.9 — above the single-env lineage's best of 113.5, suggesting the look-ahead genuinely helps in the best cases. But consistency lagged: only ~50–60% of episodes reached full length, versus the single-env policy's ~99%. Not yet as fully converged, similar in shape to where the single-env lineage sat before its final rounds.

Correction 2026-09-23

These rewards were not earned by driving. This lineage trained on vec_train_car2.usd, which still has the finite box ground collider that causes the chassis-collapse bug (§6). A collapsed, stationary car holding full throttle collects the throttle bonus (0.25 per step, 125 per 500-step episode) without ever leaving the track: replayed clones that moved 0.02–0.21 m scored 113–121, matching the reported peak of 121.9. With the ground replaced by the analytic plane, the policy leaves the track within 43–53 control steps in 20 of 20 runs — it never learned to drive. See §10.

Deployment, attempt 1

Wrong reference line, car drives into open space

First live-demo attempt reused the original shared-lane stage (simple_car.usd), whose centerline carries a +3m lane offset specific to the old single-env policy sharing a track with Car 1. The new policy trained on an unshifted centerline (each clone has its own dedicated track, no lane to share). Feeding it the wrong reference line didn't just bias the observation — it also anchored the off-track recovery threshold to the wrong line, letting the car drift up to ~7m from true center, well outside the actual curbs, before recovery even considered firing.

Mistake

Assumed the observation math being "relative" made it safe to reuse a differently-calibrated reference line. It isn't — the recovery threshold is relative to whatever reference you hand it, wrong reference and all.

Fix

Built a dedicated single-clone deployment stage with no lane offset, matching the training convention exactly.

Deployment, attempt 2

"Why does the track look bumpy?"

The road surface was built as many small per-segment boxes, raising the question of whether visible seams at the joints were destabilizing the car. They weren't — the road decal has no collision at all, so it can't physically affect the car either way — but it was a legitimate cosmetic problem worth fixing anyway: replaced with one single seamless surface spanning the whole track, later also repositioned so its top sits flush at z=0 (matching the ground plane the wheels actually rest on) instead of floating slightly above it and visually swallowing the bottom of every wheel.

A request that needed retraining

"Make it clockwise" broke the policy

Reversing the centerline's point order seemed like it should be transparent to an already-trained policy — every observation term is locally relative, not tied to an absolute direction. It wasn't: reversing which way is "forward" flips the sign of every corner's curvature, and the network's fixed weights had learned a specific left/right response to the original curvature pattern. Five reversed-direction trials from different track positions all failed within ~50–60 steps, confirmed as a real, reproducible break rather than noise.

Mistake

"The math is symmetric" is not the same claim as "an already-trained fixed-weight network generalizes to the mirrored version of what it saw." It doesn't, automatically.

Fix

None applied yet within this lineage — noted as a retraining requirement, not a code bug. The clockwise convention was carried forward into the two-car racing work below, trained fresh from the start.

Note 2026-09-23

Two notes. (1) The reversal was left in car_track_vec_env.py, so any later evaluation that imports it drives this policy against its training direction; the evaluation scripts now restore the original point order for this lineage. (2) Geometrically (z up, seen from above), the original point order of build_centerline() runs clockwise and the reversed order counterclockwise, so the racing-line and two-car lineages actually drive counterclockwise when seen from above, whatever the code comments call it.

Physical safety net

Three ways a car can quietly go wrong

Beyond drifting off-track, live deployment surfaced two more failure modes the original single-env recovery logic never had to handle: tipping/rolling under sustained throttle, and the chassis settling at the wrong height without necessarily drifting laterally. Extended the recovery check to also trigger on the car's up-vector tilting past a threshold, and on its height deviating from the expected chassis height — plus a periodic "no real progress in the last few seconds" check, since a policy weaving in place near its start point trips none of the physical checks but still isn't racing.

06 Two-car self-play racing

The next expansion: both cars racing each other, both RL-driven, sharing a single policy network so that every car's experience — whichever physical slot it's driving — trains the same weights. A genuinely different problem from solo lane-following: the observation now has to describe another agent, and the reward has to survive two cars sharing the same road without collapsing into either constant collisions or overly cautious non-racing.

Architecture

Racing pairs, not clones

Same one-process, many-clones pattern as §5, but each clone now hosts a pair of cars sharing one track rather than a single car. Observation grew to 10 dimensions: the 7-dimensional curvature-aware state plus three opponent-relative features — progress gap, lateral gap, and relative speed, each computed so the two cars in a pair see exactly opposite-signed values of each other (verified antisymmetric in a smoke test before any training). A pair resets together, as one race, whenever either car's episode ends, so the opponent-relative features are never computed against a car that just silently teleported mid-race.

The collision penalty, first attempt

Punishing racing itself, not just crashing

Added a penalty when the two cars in a pair came within 1.8m of each other, applied every physics step they stayed that close — intended to discourage collisions. First full run showed a declining full-length rate across the run (79%→44% by quartile) and worst-case rewards spiraling from bad to catastrophic (-1152 → -2569).

Mistake

1.8m is normal separation during a legitimate overtake on a 9m-wide track, not a crash — and the penalty (5.0) was roughly 15–50× larger than every other per-step reward term, applied continuously for as long as the cars stayed close rather than once per contact. Any sustained close racing — the interesting part — collapsed the reward regardless of whether the cars ever actually touched.

Fix

Reduced the penalty to 0.4, tightened the trigger distance to 1.2m (closer to actual contact). Both pathologies disappeared immediately on the next run: full-length rate stabilized (no more quarter-over-quarter decline), worst-case reward stopped spiraling, and peak reward more than doubled in the same run (43.8 → 93.95).

Training progression

A slow, steady grind

Across several rounds on the corrected reward (roughly 900k cumulative steps for this lineage), peak reward climbed 93.95 → 100.03 → 106.1, and the full-length rate settled into a tighter, more stable band (42–49%) rather than swinging wildly quarter to quarter. Average reward stayed negative throughout — the same shape the single-env lineage went through before its final consolidating rounds, not a plateau.

"Car B seems to be winning"

Checking a claim the policy itself can't explain

Since both cars run the identical shared network on symmetric, verified-antisymmetric observations, there's no mechanism by which the policy itself favors one physical car over the other. The likely explanation lay outside the network: the demo stage's two cars spawn at fixed authored coordinates rather than the paired, centerline-computed positions training actually resets to, so one starting spot could plausibly be "easier" than the other purely as spawn luck — compounded by the policy still being only ~45% converged, where any single short demo run carries real random variance in which car happens to look better.

Removing the safety net

What the raw, unassisted policy actually does

At the user's request, removed the demo's recovery/reset logic entirely — no more teleporting a car back after it drifts off-track or tips over. This immediately surfaced a failure mode the recovery net had been silently masking every time it fired.

The chassis-collapse bug — unresolved

Five fixes, zero effect

Without recovery, both cars reliably ended up stuck: chassis settled at exactly half its own box height (0.2m, precisely CHASSIS_SIZE.z / 2) with a level, non-tilted orientation — consistent with the wheels no longer supporting the body at all, rather than a simple tip-over. Reproduced this via a scripted sustained-throttle stress test (no policy involved, ruling out "bad driving decisions" as the cause) and systematically tried five different fixes: higher PhysX solver iteration counts, an order-of-magnitude lower drive force, a heavier knuckle link, explicit chassis-vs-wheel collision filtering, and a much lower commanded wheel speed.

Mistake

None of the five changed the outcome even slightly — same collapse, same resting height, same rough timing, every time. That degree of consistency across five unrelated parameters is itself informative: it rules out a tuning-sensitivity problem and points at something more structurally wrong with this stage's joint setup, likely something specific to the hand-authored ground/physics-scene configuration (versus the original single-car stage, which used Isaac Sim's own default ground-plane helper) that hasn't been isolated yet. Collision between the two cars was also ruled out as the trigger — an earlier single-car test with two cars deliberately spawned far apart from each other showed the identical collapse with no possibility of contact.

Decision

Reinstated the recovery net as a documented, practical workaround rather than continue open-ended debugging — a collapsed chassis has no physical way to recover regardless of how good the driving policy is, so no amount of further training fixes this specific failure. The root cause remains open; the next diagnostic step, if picked back up, would be comparing this stage's ground/physics-scene setup line-by-line against the original working single-car stage rather than continuing to guess at car-side parameters.

Training progression, continued

More consistent, not yet a higher ceiling

A further 1,000,000 steps (run overnight, unattended) brought this lineage to ~3.03M cumulative steps. The clearest gain was in consistency, not peak: full-length rate climbed from the 42–49% band to a 66–76% band across this run's own quartiles — a real jump in how often a race actually finishes rather than ending in a collision or an off-track excursion. Peak reward per quartile (101.1 / 95.1 / 101.0 / 105.7) landed right around the existing ceiling of ~106 rather than above it, suggesting this reward/architecture combination may be approaching its ceiling for now, distinct from the consistency gains still coming through.

Training progression, one more round

The ceiling moved after all

A further 500,000 steps (~3.53M cumulative) revised the previous read. Peak reward per quartile climbed 94.8 / 99.8 / 107.3 / 112.6 — a genuine new high, not just a repeat of the ~106 plateau, and now within reach of the single-car baseline's 105–113 band. Average reward also reached its best-yet level (quartiles −255 → −207 → −211 → −198). Full-length rate was noisier this round (81%→61%→66%→68%, below the previous round's 76% ending point) but given the reward gains this reads as ordinary round-to-round variance in a still-improving policy, not a regression. Conclusion: the "approaching its ceiling" read after the first 1M-step round was premature — there was still room.

Chasing zero resets — a controlled test

Two reward levers, one dominant cause neither could touch

Watching a live demo of this policy prompted a clear goal: fewer resets over training, ideally none. Two independent reward-side interventions were tried across three more rounds (~1.5M steps, ~5.03M cumulative): first raising the centering weight and off-track penalty and lowering the throttle bonus (mirroring exactly what worked for the single-car lineage in §1), then — after that alone didn't move the reset rate — raising the collision penalty further, on the hypothesis that two cars stuck pushing against each other under full commanded throttle is a plausible worst case for the chassis-collapse bug specifically. Both were clean, well-motivated changes; neither touched any car-side physics parameter.

The training monitor's full-length rate stayed flat across all three rounds (a 62–77% band, no trend), which by itself was ambiguous — until the live demo's new per-cause recovery breakdown made it unambiguous. Of 330 recovery-triggering control actions in one live session: off-track 0.5%, tilt 1.0%, height (the chassis-collapse bug) 98.1%, stuck-against-opponent 0.5%. After the collision-penalty change, a second session measured 390 actions: off-track 0.0%, tilt 2.3%, height 97.1%, stuck 0.6% — the dominant cause hadn't moved at all.

Finding

The flat full-length rate wasn't a sign the reward changes failed — they worked exactly as intended: off-track and tilt recoveries are both now under 3% combined, down from being a meaningful share of resets earlier in the lineage. They just couldn't move the number that was actually being watched, because that number is ~97–98% dominated by a bug a no-policy stress test had already shown fires under sustained throttle regardless of who (or what) is driving. Two independent, well-targeted reward interventions failing to shift a dominant cause is itself a controlled result, not just an inconclusive one.

One more check closed the question rather than just narrowing it: the collision-penalty hypothesis implied two-car interaction was inflating the collapse rate, so the trained policy was run driving a single car completely alone (the other car teleported off the track at startup, never touched again). Result: 100% of all recovery events (79/79) were the height/collapse bug — zero off-track, zero tilt, zero stuck-against-opponent (trivially, with no opponent present). Solo, the collapse rate is if anything higher than the two-car figure, not lower — definitively ruling out two-car interaction as a contributing cause and reconfirming, with the actual trained policy rather than a scripted stress test, that this bug is purely about sustained throttle against this stage's physics setup.

Decision

Accepted the reset rate as a documented simulation-infrastructure limitation rather than pursuing the bug's actual root cause (comparing this stage's ground/physics-scene setup against the original single-car stage, still the one untried diagnostic step). This mirrors the original 2026-09-17 call to reinstate the recovery net rather than keep guessing at car-side parameters. For the write-up: the racing policy's own driving quality is excellent by every trainable measure (off-track ≈0%, tilt ≈1–2%) — what's left in the reset rate is infrastructure, not policy quality, and that separation is now backed by a controlled before/after test rather than a single observation.

One last lever, for completeness

Maxing the off-track penalty changed nothing — as predicted

Before closing the investigation out, one more explicit request: push the off-track penalty as high as it would go and see if anything was left on the table. Raised from 40 to 150 (still a one-time terminal penalty, not per-step, so none of the runaway-suppression risk the oversized collision penalty had earlier) and trained another 500k steps (~5.53M cumulative). The policy visibly adjusted to the much larger penalty mid-run — approx_kl spiked to 0.19 and clip_fraction to 0.39 (both roughly 5–10× their usual values) — but both settled back to normal by the end of the run with no instability or NaN. Full-length rate: 71%→69%→77%→70%, the same flat band as every round since the reward rework began. Re-verified live on the new checkpoint: 100% of recoveries (57/57) still height, 0% off-track — identical to before the change.

Closing this out

Five reward-side interventions across five rounds (runs 10–14: raise centering weight, raise off-track penalty, lower throttle bonus, raise collision penalty, max the off-track penalty) took off-track driving from a real contributor to essentially zero, and left the dominant reset cause completely untouched every single time. That consistency is the actual finding: this project's reward-shaping toolkit has been pushed as far as it usefully goes on this specific problem, and what remains is a simulation-infrastructure bug, not a training one.

How often, really?

Nearly half of every decision cycle

A longer live two-car session on the final checkpoint put a number on just how frequent this is, not just which cause dominates: 3,755 recovery events out of 8,310 total control actions — 99.0% of them height/collapse (3,719), with off-track (3), tilt (24), and stuck-against-opponent (9) barely registering. That means something is being recovered on roughly 45% of every decision cycle across the session, not as a rare edge case. Watching it live, this is what reads as a car "barely moving" for a stretch — not slow driving, but a tight loop of collapsing, teleporting back, and sometimes collapsing again almost immediately, interleaved with genuinely normal driving in between.

Root cause, actually found

It was the ground collision shape all along

The "documented limitation" verdict above turned out to be premature. The user independently proposed re-examining the track rebuild itself rather than more reward tuning — exactly the one diagnostic step flagged back at the original discovery as never having been tried. Investigated concretely: the original working single-car stage builds its ground via Isaac Sim's own World.scene.add_default_ground_plane() helper; this racing stage's ground was a large scaled Cube, hand-authored directly in USD. Two differences fell out of reading that helper's source directly (isaacsim/core/api/scenes/scene.py and objects/ground_plane.py):

Attempt 6 — physics material. The helper binds an explicit PhysicsMaterial (static/dynamic friction 0.5, restitution 0.8); the race stage's ground cube had no material bound at all. Added the identical material, rebuilt, reran the stress test. No change — same collapse to z=0.200, same timing. Ruled out.

Attempt 7 — collision shape type. The helper's ground isn't a box at all — it calls PhysicsSchemaTools.addGroundPlane(), an analytic infinite plane. Replaced the finite Cube with that exact same call, kept the same physics material, rebuilt.

Result

The stress test that had failed identically every single time — five car-side parameters, one ground material, always collapsing to z=0.200 by step 50–75 — came back clean: height error 0.000 across all 400 steps, both cars, run twice for confidence. Tested against the actual trained policy next (the same solo run that had measured 100% collapse, 79/79 recoveries): 12 recoveries out of 510 actions (2.35%), down from 100%. Telemetry showed continuous, smooth lapping across nearly the full track instead of a stall-and-teleport loop.

Revised conclusion

Root cause: PhysX's box-vs-cylinder (wheel) contact generation was unstable under sustained throttle against a finite box ground collider, in a way plane-vs-cylinder contact against an analytic plane is not. Not a car-side parameter, not a missing material — specifically the ground's collision shape type. This mostly fixes the bug rather than merely working around it; a small residual rate (~2.35%) remains, so the recovery net stays in as a safety margin, but it should fire dramatically less often now. Worth stating plainly: the "accepted as documented limitation" call earlier in this section was the right decision given the evidence at the time — six independent attempts (five car-side, one ground-material) had failed identically. It just wasn't the final word, and the fix came from questioning the track construction itself rather than any further reward or parameter tuning.

A combined change regresses

Two variables, one round, a real setback

The training stage itself turned out to have the identical box-ground bug as the deploy stage — every round of training up to this point had been running against the same collapse-prone physics, not just the live demo. Fixed it the same way, and in the same round also raised the centering-penalty weight per a separate request to prioritize staying near the middle of the track. The next 500k-step round came back clearly worse, not better: full-length rate crashed to 4–6% (from the high 70s before this round), average episode length fell from ~400 to ~150 steps, and peak reward went negative in every quartile.

Mistake

Changed two things that both shift the policy's distribution at once — a genuine physics change (box→plane ground contact behaves differently) and a reward-weight change — in the same round. The policy's fine motor control had spent millions of steps tuned to the old, glitchy ground contact; asked to re-adapt to both a new physics regime and a harsher reward simultaneously, it struggled far more than either change should have caused alone. No backup of the pre-round checkpoint existed either — the training script overwrites its one checkpoint unconditionally every run — so there was no way back, only forward.

Isolating the variables

Fix one thing, hold the other steady, then recover

Two more 1M-step rounds of "just keep training" on the same combined change made only partial progress (full-length rate crept from 2% to 8% and back down to 2% — a plateau, not a recovery). The actual fix was procedural: revert the reward-weight change back to its pre-regression value, keep the ground-plane physics fix, and let the policy re-adapt to only one distribution shift at a time. That round alone beat both prior "just keep training" rounds combined — full-length rate climbed every quartile (4%→12%) and set a new all-time peak reward. Separating a physics fix from a reward change recovered faster than changing both and hoping more training would sort it out.

Severe penalties, then an overcorrection

How far is too far, for a per-step penalty

At explicit request, to punish collisions and off-track drift as hard as possible: the one-time terminal off-track penalty was raised to its practical maximum (safe, since it pays only once per episode), and the per-step collision penalty was raised from 0.8 to 3.0 — deliberately kept below the 5.0 value already known to break training outright (earlier in this section). The very next round was the best of the entire recovery arc, full-length rate climbing to 53% with a new peak reward — but the two rounds after that declined steadily, full-length rate falling back to the mid-20s% and, for the first time anywhere in the recovery, failing to set a new peak reward at all.

Mistake

3.0 looked safe purely because it was under the known-broken 5.0 — but "not the exact value that broke it before" isn't the same as "safe." It reproduced the same runaway-suppression pathology, just more slowly: a policy discouraged this strongly from any sustained contact starts trading away genuine racing behavior to avoid the penalty, and it took two rounds of training data to show up clearly instead of one.

Fix

Backed the collision penalty off to 1.5 — roughly double the original pre-experiment value, still meaningfully more severe than before, but with real headroom below the failure point. The very next round confirmed the correction: after a rough start still carrying the prior decline's momentum, it recovered mid-round back to the ~50% level, and every round since has held a consistent, high plateau.

Back to baseline, and past it

The recovery arc closes

Across the rounds following the collision-penalty correction, full-length rate climbed past the original pre-regression baseline (71–77%) for the first time since the regression, reaching 75–76% in one round and settling into a sustained 69–89%-per-quartile plateau over several more, with peak reward continuing to set new highs periodically (past 215) and mean reward turning solidly positive for most quartiles — something that had not happened anywhere earlier in this lineage. A fully sustained 90%+ across every quartile — the point where the recovery/reset net could plausibly be retired rather than just relied on less often — is close but not yet reached.

Lesson kept

The near-total loss of the pre-regression checkpoint motivated adding real checkpoint versioning to the training script: every round now optionally saves a labeled backup alongside the live checkpoint, so a future regression can be rolled back to a specific known-good round instead of only ever training forward through the damage.

The long plateau, and a step past it

From "close to 90%" to the best round in the lineage's history

Seventeen more 1,000,000-step rounds (run32 through run49, ~17M further steps, ~40M cumulative) held a noisy but genuinely elite plateau — round-average full-length rate mostly in the 80–91% band, with individual quartiles crossing 90% outright for the first time (run39: three consecutive quartiles above 90%, a first for this lineage, alongside a new peak reward of 221.6). The plateau kept climbing rather than flattening: run48 set new all-time records on every axis that matters — the highest single-quartile full-length rate ever recorded (93.2%) and the highest quartile mean reward ever recorded (147.3), with a round-average full-length rate above 91%.

Lesson repeated

Round-to-round variance stayed real throughout — several rounds dipped mid-round to 60–70% full-length before recovering by their own final quartile, the same self-correcting shape seen earlier in the recovery arc. None of these dips were treated as regressions; only a round that failed to recover by its own end would have qualified, and none did across this whole stretch.

09 Reward redesign: speed, competition, and smoothness

§7 left the new-track adaptation two rounds in, already most of the way back to par. Ten more rounds (newtrack_run3–12, ~10M further steps) closed the rest of that gap and then went past it — full-length rate reached 100% in places and peak reward crossed 200, matching or beating the original-track lineage's own best numbers. That should have been the end of the story. It wasn't: the aggregate metrics kept climbing while the actual driving quietly got worse in ways full-length rate and mean reward don't measure at all, and finding that gap — and closing it — is the subject of this section.

A feature built to answer a suspicion

Ten laps, timed, per car, before trusting a demo impression

A second complaint, from watching, not measuring

"One car just follows the other"

Live-demo observation on the same run12 checkpoint: the two cars weren't racing so much as convoying, one consistently trailing the other rather than contesting position. The cause traced cleanly to the reward's own design: neither car's score depended at all on its position relative to its opponent — only individual progress plus the shared collision-avoidance penalty from §6. With nothing to gain by contesting the lead, self-play had converged to a safe follow-the-leader equilibrium instead of an adversarial one.

Two conservative fixes, one training arc

More throttle, and something to actually fight over

Two changes, in one round, both kept deliberately modest against the project's own repeated lesson (the §6 COLLISION_PENALTY=5.0 incident) that an oversized new per-step term reliably breaks training: THROTTLE_BONUS_WEIGHT doubled (0.15→0.30) to push back against the low-throttle drift, and a new OVERTAKE_INCENTIVE_WEIGHT=0.3 rewarding a car for gaining ground on its opponent each step — computed from the change in the existing opponent-progress-gap observation feature, so the two cars in a pair always get exactly opposite-signed values. Zero-sum by construction: it redistributes reward toward contested racing rather than inflating the total budget, which is precisely what kept it safe at this weight.

Result

Two rounds (newtrack_overtake_run1–2, ~2M steps) showed no sign of the runaway-suppression pattern — full-length rate held 93–99% throughout, and worst-case reward outliers improved. Re-benchmarked on run2: 23.75s / 23.70s mean laps — about two-thirds of the way back from the 25.8s regression toward the 22.4s baseline. Partial, not full, recovery.

A new problem, caused by the fix for the old one

Faster and more competitive, also jerkier

Watching the overtake-fix demo surfaced a third complaint: visibly jerky driving. Both new terms reward bursty control — hard acceleration to close a gap, sharp braking into a corner — and nothing in this reward penalized the resulting throttle/steer whiplash, unlike the single-car baseline, which had already solved exactly this problem once (§7) with a measured 18.6% reduction in action jitter. Mirrored that fix exactly: SMOOTHNESS_PENALTY_WEIGHT=0.08, penalizing the per-step change in consecutive throttle and steer commands, at the identical weight that had already been proven safe on the single-car lineage.

Correction 2026-09-23

The jerkiness was not caused by the two new terms. The action delta after newtrack_overtake_run2 (0.124) was no higher than after newtrack_run12 (0.141), before either term existed; it had built up unnoticed during the plain adaptation rounds. The smoothness term did reduce it (0.087 after smooth_run1, 0.064 after smooth_run20).

The smoothness arc, and an elite regime that held

From "no jitteriness" to the best rounds this lineage has ever run

The very next round's demo drew a direct, positive confirmation: "looks impressive no jitterness as of now." Training continued round over round (newtrack_smooth_run1–34 at the time of this writing, well past 85M cumulative steps for the whole two-car lineage) with occasional ordinary noise — a handful of rounds dipped mid-run and self-corrected by their own final quartile, the same shape seen throughout the §6 recovery arc, never treated as a regression because none of them failed to recover. Starting around run18, the lineage stepped into a genuinely new regime: three consecutive perfect (100%) full-length quartiles, a new all-time peak reward of 233, and the per-quartile minimum reward barely dipping negative — meaning nearly every single episode, not just the average, was racing well. Elite training statistics, not better driving. A stall, caught once, watched for, never seen again

Two cars, bogged down together, for two minutes

The first post-smoothness-fix benchmark (run1) was mostly excellent — clean laps at 23.06s/22.85s, matching the pre-regression baseline — except for one shared incident: Car A's laps 5–6 and Car B's lap 5 all ballooned to 55–125 seconds, their timestamps overlapping almost exactly, before both cars snapped back to normal ~22s pace for the rest of the race. Verdict

Treated as a watch item rather than a fix-immediately bug, per explicit instruction to keep training and watch for a recurrence. One training round did show three unusually severe single-episode reward outliers where earlier rounds had shown at most one, but the very next round dropped back to zero, and full-length rate never wavered through any of it. A decoration that was never where it claimed to be

A late, unrelated report while watching a demo: no line visible at the start position, only at what looked like the finish. Mistake

The line was purely a visual decoration from the start — lap detection (the number that actually matters) has always worked from cumulative progress delta, never from physically crossing the drawn tiles — so this never once touched a training number, a benchmark result, or any reward. Fix

Replaced the hardcoded points[0] reference with the centerline segment nearest the cars' actual spawn coordinate, rebuilt the stage, and re-verified live. The multi-pair training stage never had this line at all (headless-only, never rendered), so nothing there needed touching.

A test built to settle it: swap the starting spots

A spawn-spot effect on run4 — and a first explanation that turned out to be incomplete

Wrote a one-off diagnostic (mirroring lap_time_benchmark.py exactly, but swapping Car A and Car B's starting world poses right after the stage loads) and re-ran the same benchmark. Finding

The win moved with the physical spawn point, not with the car. This is the identical confound already caught once in §8's head-to-head test — a fixed, unrandomized starting position dominating an outcome that looked like it was about policy quality — recurring in a different script that had simply never been checked for it. build_unknown_track_deploy.py spawns Car A and Car B at two fixed coordinates, (0,−1.5) and (0,1.5), identically every single demo and benchmark run; one lateral line is evidently mildly favorable into the track's first corner, so whichever car lands there wins deterministically, every time, regardless of actual driving skill — both cars share one identical policy network. For the run4 checkpoint this reading was right as far as it went; the entries below show it was not the whole story.

Note 2026-09-23

Position B, (0, +1.5), is on the inside of the first corner: the cars drive counterclockwise seen from above, so every corner is a left turn. The fix that froze the demo

Exactly 90 control actions, twice in a row

Relaunching the visible demo with the runtime swap in place, the simulation stopped advancing about three seconds in. The window stayed visible, in front and responsive and the GPU stayed busy, but the telemetry and action logs stopped at precisely 360 physics steps (90 control actions) — identically on two consecutive launches. A copy of the script with the swap block removed ran continuously well past that point. The swap called world.step() twice and teleported both cars before world.play(); the headless benchmark and race evaluation tolerate that because they never call world.play(), but the rendered demo loop does not.

Mistake

An earlier launch of the same demo had been written off as "stuck loading" because its ready-file never appeared — but the demo scripts write that file to the thesis root, and the check had been polling a different folder. That diagnosis was wrong, and the demo had very probably been frozen for the same reason all along.

Fix

Moved the swap into the stage itself, before physics starts. Each car is seven independent rigid bodies (chassis, four wheels, two steering knuckles), each a direct child of its car prim with its own world-space translate, so shifting all seven by the chassis-to-chassis offset relocates the whole car with no runtime teleport and no extra steps. Verified with the swap forced on: the log confirmed it, Car A's starting side flipped, and the demo ran continuously past the old freeze point. The headless scripts keep their runtime swap, which works there.

Correction

The earlier verdict in this section, that the "one car always wins" pattern was a spawn-point artifact "rather than any policy or reward flaw", was incomplete. The spawn point mattered for run4, but the underlying behavior is a property of the policy: a follow-the-leader lock-in. Whoever is marginally ahead after the first corner stays about 13 m ahead, and the follower yields — dropping to roughly 2 m/s in the corner — instead of contesting. That is consistent with the per-step collision penalty (1.5 within 1.2 m) teaching the follower that giving way is cheaper than racing (§10), and it explains why raising the overtake incentive and adding millions of steps produced no overtaking. It also means the lap-time benchmark is a poor test of racing fairness; paired, mirrored starts are the right design. Staggered longitudinal starts during training were tried next (the two entries below) and did not help; still untried: a lower collision penalty or trigger distance, a reward paid for completing a pass, and asymmetric-role self-play.

Trying to break the lock-in

Staggered starts in training: 100M → 103M steps

Every training episode so far started with the two cars exactly side by side, so the policy never had to overtake — the natural first attempt at the lock-in was to change the start distribution and nothing else. An opt-in stagger_prob was added to the training environment (off by default, so demos and evaluations are unchanged): in 75% of resets the trailing car starts 1.5–8 m behind the leader along the centerline, on a random side, with either car leading. Rewards were left untouched, so any change would come from the starts alone. A smoke test confirmed the staggered resets (gaps 1.65–8.2 m, no start closer than 3.4 m, observations still exactly antisymmetric). Both policies drive at essentially the car's top speed (flying laps of about 21 s on a 126.8 m track, 6 m/s maximum), so the difference between them is small: in clean racing the racing-line car is about 0.5% faster, plausibly because its weak centering penalty lets it use the track width, whereas the self-play policy was trained to stay near the centerline (weight 0.9). What decides a single heat is what happens when the cars meet. In the original fixed-start lane assignment, the two cars leave the grid side by side and, without the net, stay within 2 m of each other for 4,941 of 5,000 steps — wheel to wheel, neither able to pass — which slows both to about 32.6 s laps. With the net on, a brief height event during that contact (step ~917) started a ~500-step loop in which both cars were teleported onto the centerline next to each other and re-triggered each other's height check; that loop is an artifact of the net, not of either policy. The earlier "racing-line covers 19% more distance" came from the collapse bug and is withdrawn. The racing-line policy is marginally faster, not decisively better; the opponent-aware self-play policy does not win races against it either. Both policies occasionally leave the track after coming close to the other car.

Behavioral cloning, re-examined

The demonstrations were driven the wrong way round

Analysing the three recorded datasets (human_driving_data*.npz) instead of the fine-tuning curves: every sample has cos(heading error) < 0 (means −0.91, −0.98, −0.98), and the recorded yaw rate is positive, i.e. left turns. The RL environment of the single-car baseline runs the original vertex order, clockwise seen from above, and resets every episode within ±0.1 rad of the track direction (cos ≈ 1). The cloned actor was therefore fitted to states the RL task never visits. In addition, record_driving.py computes Car 1’s observations with Car 2’s shifted reference line, so the demonstrations sit 2–3 m off that line (31% of dataset 1 beyond the off-track margin), and keyboard input makes every action 0 or ±1.

The consistent failure across three datasets and five fixes is explained by a shared data mismatch, not by the technique. A valid test would record demonstrations in the task's direction of travel, relative to the same reference line, with continuous (gamepad or wheel) input. Why the incentive could not work

Identical cars, a speed cap, and a reward too small for the risk

Three reasons. Physics: both cars are identical, driven by the same deterministic network, and both reach the same 6 m/s top speed on every straight; a follower can gain only through a shorter line in the corners, which the leader already occupies, or through a mistake of the leader. Scale: at a weight of 0.5, gaining one car length (2 m) is worth 1.0 — less than the proximity penalty for a single step within 1.2 m (1.5) — and over an episode the term telescopes to at most 0.5 × 30 = 15, while a failed pass costs 150 and ends the pair's episode. Symmetry: the term is zero-sum between two cars driven by the same parameters, so every gain in one role is a loss in the other, and holding position satisfies both. Following at a safe distance is a stable outcome of this game.

Next time

Make overtaking possible and worth it: opponents of different strength (earlier checkpoints, a league), start configurations behind a slower opponent, a reward paid when a pass is completed rather than per step, and the race evaluation above as the test.

Both tracks, both ways

No forgetting — and run49's weak spot was the start

The final policy, 55 rounds after it last saw the original track, still drives it in all 12 heats without incident (21.43 s flying laps, 1.9% slower than run49). Run49 itself drives its own track at top speed and practically on the centerline (21.03 s, 0.07 m offset), but had incidents in 6 of its 12 heats, 4 of them off the track, all within the first 250 steps after the side-by-side start, when the two cars came close. Twelve deterministic heats are a small sample, but the start was evidently the weakest part of that policy.

Which round had the 5.0 penalty, and what the logs say about Runs 2–3

The oversized collision penalty (5.0 within 1.8 m) was in effect for the first two two-car rounds (a 20k-step validation round with 3 pairs, then the first 200k-step round with 8 pairs, whose mean episode length fell from 469 to 287); the 0.4 / 1.2 m fix came with round 3. What following the instructions exposed

Three things a stranger would have tripped over

Mistake

Every script in the published repository contains the absolute path of this laptop's working folder, C:/Users/sanja/Desktop/thesis — 177 times in 65 files. As published, nobody else could run anything without editing every script. Rather than rewrite all 65 files, the manual gives a one-command PowerShell replacement, tested on a fresh clone (it changes only those path strings), and the README now points it out.

Finding

The summary block of a race-evaluation file averages over all heats, while the thesis tables average lap time, offsets, action delta and gap over the heats without incident. A reader recomputing from the summary would get 23.85 s for overtake_run2 instead of the thesis's 23.21 s and suspect an error. The two agree only when every heat is clean. The manual now says so, and the check script computes the incident-free values, which match the thesis exactly.

Finding

Re-running an evaluation writes back to the committed file, and git diff then shows changes even when every number is identical: the stage line records the folder of the copy, and newer versions of the scripts record fields the older files predate (lap_marks and path_x_y_speed per heat, a "ground": "asbuilt" label). Checked field by field: nothing that was already there changed. Documented in the manual so a diff is not mistaken for a discrepancy.

The real gap

Publishing every per-round checkpoint

Until now only the final model of each lineage was on GitHub; checkpoint_backups/ was gitignored as an internal safety net. The results of intermediate checkpoints — the 450k baseline, run49 (zero-shot transfer and the head-to-head), competition rounds 4 and 6, the discarded staggered model — could therefore be read but not re-run: 7 of the 18 claims in the manual depended, at least in part, on files nobody else had. Now published: 87 checkpoints, 14 MB, one per training round, from original-track rounds 27 and 29–49 through every stadium round to the 100M milestone and the three staggered rounds; only a smoke-test checkpoint stays excluded. Every file was checked first — standard Stable-Baselines3 checkpoints with no personal paths inside — and 100M_milestone is byte-identical to newtrack_compete_run11 and to the live car_race_ppo_model.zip. They were committed directly rather than attached to a GitHub release, so a plain clone has everything; the README gained a table mapping each checkpoint label to its thesis round and step count, and check_results.py sits at the repository root (commit 3da0aff).

Result

Every one of the 18 headline claims in the thesis can now be re-run from a fresh clone of the repository, and the run49 evaluation, previously impossible to repeat outside this laptop, was repeated on one and matched.
