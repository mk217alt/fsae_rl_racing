Engineering journal — Isaac Sim / Isaac Lab / stable-baselines3

From a crashing simulator to a car that drives itself

The complete record, start to end, of the thesis project itself — Reinforcement Learning for Autonomous Racing of a Formula Student Vehicle in NVIDIA Isaac Sim: getting Isaac Sim to even launch, early RL-toolchain validation with Isaac Lab, and then building a car, a track, and a policy that learned to drive it — and eventually race another car — through nothing but trial and error.

01 How the training actually works

Car 2 learns by trial and error, not by copying Car 1's human driving. Every physics step, it looks at where it is relative to the track centerline, picks a throttle/steer action, and gets scored on how well that worked. Repeat that a few hundred thousand times and a driving policy falls out.

Observelateral offset, heading error (sin/cos), forward speed, yaw rate
Decidepolicy network outputs [throttle, steer] ∈ [−1, 1]
Actjoint velocity/position targets on the front wheels
Simulate4 PhysX steps in Isaac Sim (headless)
Scorereward = progress − centering penalty + throttle bonus
PieceChoice
EnvironmentCustom Gymnasium env (car_track_env.py) wrapping Car 2's Articulation directly — not an Isaac Lab task, see §4
AlgorithmPPO, stable-baselines3, MlpPolicy, CPU device
Observation (5)[lateral_offset, sin(heading_error), cos(heading_error), forward_speed, yaw_rate]
Action (2)[throttle, steer], continuous, applied every 4 physics steps
Episode resetRandom segment along the track each episode, not always the same start line — more varied training signal
Episode end500 steps, or lateral offset exceeds the track's off-road margin

The reward went through three revisions as priorities were set explicitly, each time by widening the gap between "stay centered" and "go fast":

Run 4 was killed partway through (§2, Phase 9) when the weights were revised again before it finished, so it never produced a checkpoint — Run 5 resumes cleanly from Run 3's saved policy instead. Runs 6 and 7 changed nothing about the reward — same Run 5 weights, another 200k steps total, to see whether an already-converged policy had more to give. It did, up to a point: Run 6 climbed reward from the 89–104 range to 108–113; Run 7 held at that level (105–113) rather than climbing further, the expected shape of a policy that has essentially converged.

Deployment (run_dual_car.py) reuses the exact same centerline math as training — both files import build_centerline() from car_track_env.py — specifically so the policy never sees a different coordinate convention live than it trained on. It also carries a safety net: if Car 2 ever drifts past the off-track margin during the live demo, it's teleported back onto the centerline wherever it currently is (not the start line) so it keeps lapping instead of getting stuck for good.

02 Every mistake, in order

Nothing here worked on the first try. Kept in order because the fixes build on each other — including the two phases before the car project even existed.

Phase 1 — Isaac Sim itself

The simulator wouldn't even start

Before any of this existed, Isaac Sim 5.1.0 crashed on every launch inside its RTX renderer (rtx.scenedb.plugin.dll), consistently, within the first few seconds.

Mistake

Assumed it was this laptop's hybrid NVIDIA/AMD graphics fighting each other, and spent real effort ruling that out — disabling third-party Vulkan overlay layers (Steam, Discord, GeForce Experience) one by one, then restricting the Vulkan loader to only the NVIDIA ICD via VK_ICD_FILENAMES so the AMD GPU couldn't be involved at all. The crash persisted through every one of those tests.

Fix

The real cause was simpler: the newest GPU driver branch (610.x) is unvalidated for this Isaac Sim build. Rolled back to driver 580.88, the officially validated version — confirmed against the exact crash signature in public Isaac Sim issue trackers. A second, unrelated Code 43 GPU error surfaced right after that install, traced to a power-management setting and a conflicting Windows Update driver push.

Phase 2 — Isaac Lab, validating the toolchain

Four dependencies, each broken by fixing the last one

Before committing to the thesis's actual vehicle-racing environment, Isaac Lab was installed and exercised on a stock example task — training a Franka arm to pick up a cube — purely to validate that the RL toolchain (Isaac Lab, rsl_rl, PPO) worked end to end on this machine at all, independent of any project-specific code.

Mistake

Installed the main branch first, which requires Python 3.12 — but Isaac Sim 5.1.0 ships Python 3.11. Switched to the matching v2.3.2 release tag, which then hit a chain of its own: a pinned dependency (flatdict) failed to build because its isolated build environment couldn't find pkg_resources; installing it manually pulled in a newer tensordict that crashed on import with a native access violation (an ABI mismatch against the pinned torch version); downgrading tensordict to match dragged numpy to a version Isaac Lab explicitly forbids; fixing numpy broke h5py the same way.

Fix

Each link was pinned to the exact version compatible with the one before it (flatdict==4.0.1 built with --no-build-isolation, tensordict==0.7.2, numpy<2, h5py==3.12.1) until the whole chain held together. Validated the entire pipeline by training a Franka arm lift-cube task with rsl_rl PPO — real learning, confirmed end to end. With the toolchain proven, the actual thesis work — the car, the track, and an RL policy learning to race it — followed directly.

Phase 3 — building the car

Decorations warped by their own parent's scale

A Formula-style body kit (nose cone, sidepods, wheel arches) was attached under the chassis rigid body.

Mistake

The chassis was a scaled Cube acting as both the collision shape and the rigid body. Every decoration parented under it silently inherited that same non-uniform scale, stretching and mispositioning every piece.

Fix

Rebuilt the chassis as a plain Xform "link" with the sized Cube as a child collision shape — the standard PhysX authoring pattern. This fixed the scale bug outright, but exposed a second, deeper problem next.

Phase 4 — building the car

A duplicate car that wouldn't go away

Even after the scale fix, a frozen "ghost" copy of the decorated car rendered alongside the live, driving one.

Mistake

Diagnostic scripts confirmed the saved USD file only ever contained one car hierarchy — so this wasn't a data bug. It was traced to Isaac Sim's Fabric simulation cache and the regular USD render delegate drawing the same rigid body from two different sources at once. Forcing /physics/updateToUsd and disabling the Fabric scene delegate didn't resolve it.

Fix

Removed the decorative body kit entirely and kept the plain functional car, which had always rendered correctly. The open question — nested cosmetic geometry under a simulated rigid body — is parked for a future attempt (single baked mesh, most likely).

Phase 5 — building the track

Corners landed 224 meters away

The rounded-square track is built by placing thin box segments along a computed polyline, each scaled, rotated, and translated into place.

Mistake

USD composes transform operations in the reverse of the order they're added — the last op added acts on the geometry first. Adding Scale → Rotate → Translate actually executed as Translate → Rotate → Scale, so every segment's position was itself getting rotated and scaled before placement.

Fix

Proved it with a two-line isolated test (translate (10,0,0), rotate 45°, scale (2,1,0.4) → read back — got (14.14, 7.07, 0), exactly what reversed composition predicts). Reordered every call site to Translate → Rotate → Scale, then added a standing verify_track.py that reads back world positions before any new track geometry is trusted.

Phase 6 — the RL environment

Driving forward paid a penalty

First smoke test: constant forward throttle, straight wheels — and the reward got steadily more negative as the car sped up.

Mistake

The reset logic pointed the car 180° opposite the track polyline's own direction of travel, reasoning that applied to only one specific spawn segment but was applied everywhere. "Forward" in the car's own frame corresponded to decreasing progress along the track.

Fix

Dropped the extra 180° flip so the car's nose matches the polyline's own direction at every segment. Re-ran the same smoke test: reward now rises cleanly from 0.004 to 0.18 as speed builds — confirmed before any real training was ever launched.

Phase 7 — training iterations

Coin-flip reliability at 50k steps

The first full training run showed real learning, but roughly half of all episodes still ended in a crash off-track.

Mistake

N/A — this was the reward function doing exactly what it was told to; centering and off-track penalties simply weren't weighted heavily enough yet to dominate the policy's behavior.

Fix

Reprioritized explicitly: stay centered first, accelerate second. Raised the centering penalty and off-track penalty, added a dedicated throttle bonus, and kept training from the same checkpoint rather than starting over. By 150k cumulative steps, the last 25+ episodes were all full-length with steady reward in the 46–63 range.

Phase 8 — going in circles, briefly

Stuck for two minutes, then fine

The first live demo of the 150k-step policy was watched only through a periodic position-telemetry log — this session has no way to see the rendered Isaac Sim window directly.

Mistake

Telemetry showed Car 2 barely creeping (about 0.16 m of net movement) for roughly 140 seconds of sim time, right after the auto-recovery teleport fired twice in quick succession — consistent with being physically wedged against a curb, though not conclusively diagnosed.

Fix

Not yet isolated at the time — it recovered on its own and drove smoothly for the rest of the ~15-minute session. See §5 for how this resolved with later policies.

Phase 9 — editing a running process

Changing the reward mid-flight did nothing

Asked to push the reward weights even higher while a training run was already in progress.

Mistake

Python had already read the old constants into memory when the training process started; editing the source file on disk has no effect on a process already running.

Fix

Stopped the in-flight run, accepted the loss of its unsaved partial progress (checkpoints are only written at the very end of each invocation, not incrementally), and restarted from the last saved 150k checkpoint with the new weights.

03 The behavioral-cloning experiment — a negative result

With Run 5's pure-RL policy converged, the next idea was to make Car 2 drive more like its human-driven counterpart: record actual driving, pretrain the policy network on it, then let PPO fine-tune from that starting point instead of from scratch — hoping for a policy that both converges faster and drives in a recognizably human style. It didn't work, across three full rounds and five separate fixes, and the reason it didn't work turned out to be more interesting than any of the individual bugs.

Round 1, setup

Recording a human baseline

record_driving.py drove Car 1 by keyboard for several laps, sampling (observation, action) pairs at the same decision cadence the RL environment trains at (every 4 physics steps) — 2,608 samples in total. pretrain_bc.py then fit Car 2's policy network to reproduce those actions via supervised MSE regression, no simulator needed for this step. Training loss converged smoothly from 0.197 to about 0.041 over 300 epochs.

Round 1, attempt 1 — direct fine-tune

A well-fit mean, buried in noise

Handed the BC-pretrained policy straight to PPO for 50k timesteps of fine-tuning.

Mistake

BC only regressed the policy's action mean. Its action-noise parameter (log_std) was left at stable-baselines3's default of 0.0 — a standard deviation of 1.0, enormous next to a [−1, 1] action range. Every rollout PPO actually collected sampled almost pure noise instead of the well-fit mean: episode length collapsed from 137 to 81 steps over the run and reward never rose above −37.

Fix

Tightened log_std to a standard deviation of 0.15 before handing the policy to PPO. This fixed the noise problem specifically — but not the underlying outcome, as the next two attempts showed.

Round 1, attempt 2 — warm-start the critic too

Fixing the noise didn't fix the plateau

With sane action noise, reward was still deeply negative and, oddly, episode length kept falling as training went on rather than recovering. Working theory: BC pretraining only ever touched the actor, so the critic (value network) started completely uncalibrated — its early advantage estimates were close to random, and PPO trusted them enough to actively degrade the good BC actor before the critic could catch up.

Mistake

Confirmed by collecting 40 real rollout episodes under the frozen BC actor and regressing the critic alone on their Monte-Carlo returns (warmup_critic.py) — first pass silently failed because env.close() was called before the regression step ran, tearing down the whole Isaac Sim process mid-script.

Fix

Moved env.close() to the end of the script. The warmed critic's loss dropped roughly 13× (4313 → 286 train, 4242 → 323 validation) — genuinely learned to predict real returns. Fine-tuning from this checkpoint no longer showed the sharp degradation, but reward still plateaued: −83 to −117 across every quarter of a 50k-step run, max reward never above −37, and the fraction of full-length episodes actually fell as training went on (13 → 7 comparing the first and last quarter).

Round 1, attempt 3 — slow the updates down

Same ceiling, reached more gently

Hypothesis: the default PPO learning rate (3×10⁻⁴) was simply too large a step for nudging an already-good policy — each update could be knocking the actor back out of the good BC basin about as fast as the critic stabilized it.

Mistake

N/A — this was a reasonable hypothesis, tested cleanly rather than a bug.

Fix

Verified the override actually took effect (PPO.load(..., learning_rate=5e-5), confirmed against the loaded schedule) before committing to a full run, then trained 100k timesteps at 6× lower learning rate. Reward crept up slightly then flatlined at the same ceiling as attempt 2 (−96 → −76, plateauing there), max reward capped at −36, and the full-length episode share shrank again (7% → 4%) over the run.

Round 1, interim verdict

A tempting explanation — driving style

After round 1, the leading theory was that the recorded driving style itself was the problem: the reward function penalizes lateral drift from the centerline heavily (−0.6 × offset every step, plus a hard −30 for leaving the road), and human driving — however competent-looking — might simply hug lines, brake, and countersteer differently than this specific reward rewards. That theory made a clear prediction: driving more deliberately centered the second time around should raise the ceiling. It didn't.

Round 2 — better data, same ceiling

Testing the driving-style theory directly

Re-recorded from scratch (1,841 samples, this time deliberately hugging the centerline) and reran the full pipeline with all three round-1 fixes applied from the start instead of rediscovered one at a time. The early signal looked genuinely promising: sampling the raw BC actor's rollouts (before any RL fine-tuning at all) showed episodes surviving far longer than round 1's data ever produced — 4 of 40 episodes already reached the full 500-step length, versus essentially none before.

Mistake

N/A — the setup was correct; this was a genuine test of the driving-style hypothesis, not a bug hunt.

Fix

None needed — the pipeline ran clean end to end. But 100k timesteps of fine-tuning landed on essentially the identical ceiling as round 1: max reward −37 (round 1's was −36), and the fraction of full-length episodes fell across the run just as before (12% in the first quarter down to under 3% by the last), despite starting from a measurably better-surviving BC actor.

Round 3 — smaller data, same ceiling again

One more independent try, for confidence

A third recording (1,422 samples — smaller than either previous dataset, driven with deliberately varied speed and line rather than one consistent style) ran through the identical pipeline: BC pretrain with log_std already tightened, critic warmup, then 100k timesteps of fine-tuning at the same low learning rate. This wasn't testing a new hypothesis — round 2 had already ruled out driving style — it was a direct replication check on a fully independent dataset before treating the conclusion as settled.

Mistake

N/A — clean run, no bugs.

Fix

None needed. Max reward reached −28.2 — a small edge over rounds 1 and 2 (−36, −37), well within the noise of a stochastic policy, not a meaningfully higher ceiling. The same shape repeated once more: full-length episodes made up 8.5% of the first quarter and fell to 3.7% by the last, reward stayed deeply negative throughout (quartile averages −143 → −93 → −81 → −72).

Verdict

Three datasets, five fixes, one unmoved ceiling

Three independently recorded human driving datasets — natural, deliberately centered, and deliberately varied — of three different sizes (2,608 / 1,841 / 1,422 samples), landed on the same ceiling after five genuinely different fixes (action noise, critic calibration, update step size, plus two clean replications). That rules out both the driving-style theory and a data-volume theory: if either were the real constraint, at least one of three independent attempts should have moved the number, and none of them did. What every round shared instead is the technique — behavioral cloning from a small human dataset, then PPO fine-tuning, against this specific reward and termination boundary. The most likely remaining explanation is that BC pretraining on a small demonstration set gives PPO a confident but narrow starting point — fit tightly to the states the demonstrations happened to visit — while pure RL, having no such basin to begin with, explores broadly from the start and simply needed its own large budget (250k+ steps) to get there rather than a shortcut through imitation.

Decision

Accepted the pure-RL policy (car2_ppo_model.zip, now 450k cumulative steps after Runs 6–7, reward 105–113) as the final result and closed out the BC line of work for good. Three well-motivated, carefully executed rounds that all failed the identical way is about as strong a negative result as this kind of experiment produces — not a stalled investigation, a settled one. It says something specific and citable for the write-up: imitation-learning warm-starts don't help RL here, and it isn't for lack of trying different data or different fixes.

04 Roads not taken

Three real forks, each decided against a stated constraint rather than by default.

Learning method
✓ Chosen — reinforcement learning

Learns purely from trial and error against a reward function. Self-corrects from states it's never seen, at the cost of needing many more environment steps than a supervised approach.

Considered — imitation learning

Record Car 1's human (state, action) pairs and train a supervised model to copy them. Faster to set up and directly uses the human data, but compounds errors on situations the demonstrations never covered — rejected because it can't recover from its own mistakes. (A hybrid — using it only as an RL warm-start, not as the final policy — was tried later anyway, three times, with three different recordings; see §3.)

Training framework
✓ Chosen — custom Gymnasium env

A lightweight environment written directly against the core Isaac Sim Articulation API. Minutes to iterate on, since the car and track are hand-authored USD, not registered Isaac Lab assets.

Considered — Isaac Lab task

The same manager-based framework validated on the Franka arm in Phase 2, with proper task registration and massively parallel environments. More correct for a production task, but registering a new task there is real overhead for a two-car demo track — deferred.

RL library
✓ Chosen — stable-baselines3

A plain gymnasium.Env in, PPO out — the generic single-environment API fit a hand-rolled env with no extra glue code.

Considered — rsl_rl

Already proven on the Franka arm task and faster per-sample at scale, but its runner expects a specialized vectorized-env interface built for thousands of parallel Isaac Lab environments — a mismatch for one car on one track.

05 Parallel training and curvature look-ahead

With the single-env pure-RL policy accepted as final, the next round pushed on two of the "not yet tried" items from §4 at once: speed up training by running many car instances at once, and give the policy a look at the road ahead instead of only its current position.

Architecture

One Isaac Sim process, many clones

True parallel Isaac Sim processes were never an option on this machine — running two kit.exe at once was already known to cause severe resource contention. The actual answer, matching how Isaac Lab itself scales: clone the car+track N times inside one stage, and drive all of them with a single batched Articulation view over a wildcard/list of prim paths. One world.step() call already advances every clone's physics at once, so N cars costs far less than N times the wall-clock — no multiprocessing needed.

Result

Validated first at 6 clones via a smoke test (no crash, curvature values varied correctly per clone), then scaled to 10. Measured throughput: ~152–196 timesteps/second, roughly 2× the original single-env pace (~80/s) — confirmed empirically, not assumed.

Observation change

Seeing the corner before it arrives

Added two dimensions to the observation: sin/cos of the heading change 5 meters ahead along the centerline ("curvature look-ahead"), so the policy can anticipate a turn rather than only react to its current lateral offset. Observation grew from 5 to 7 dimensions — a different input shape than the accepted single-env policy, so this is necessarily a fresh network, not a continuation.

Training results

A higher ceiling, less consistently reached

Across 6→10-clone runs totalling 470k steps, peak reward reached 118.9, later 121.9 — above the single-env lineage's best of 113.5, suggesting the look-ahead genuinely helps in the best cases. But consistency lagged: only ~50–60% of episodes reached full length, versus the single-env policy's ~99%. Not yet as fully converged, similar in shape to where the single-env lineage sat before its final rounds.

Deployment, attempt 1

Wrong reference line, car drives into open space

First live-demo attempt reused the original shared-lane stage (simple_car.usd), whose centerline carries a +3m lane offset specific to the old single-env policy sharing a track with Car 1. The new policy trained on an unshifted centerline (each clone has its own dedicated track, no lane to share). Feeding it the wrong reference line didn't just bias the observation — it also anchored the off-track recovery threshold to the wrong line, letting the car drift up to ~7m from true center, well outside the actual curbs, before recovery even considered firing.

Mistake

Assumed the observation math being "relative" made it safe to reuse a differently-calibrated reference line. It isn't — the recovery threshold is relative to whatever reference you hand it, wrong reference and all.

Fix

Built a dedicated single-clone deployment stage with no lane offset, matching the training convention exactly.

Deployment, attempt 2

"Why does the track look bumpy?"

The road surface was built as many small per-segment boxes, raising the question of whether visible seams at the joints were destabilizing the car. They weren't — the road decal has no collision at all, so it can't physically affect the car either way — but it was a legitimate cosmetic problem worth fixing anyway: replaced with one single seamless surface spanning the whole track, later also repositioned so its top sits flush at z=0 (matching the ground plane the wheels actually rest on) instead of floating slightly above it and visually swallowing the bottom of every wheel.

A request that needed retraining

"Make it clockwise" broke the policy

Reversing the centerline's point order seemed like it should be transparent to an already-trained policy — every observation term is locally relative, not tied to an absolute direction. It wasn't: reversing which way is "forward" flips the sign of every corner's curvature, and the network's fixed weights had learned a specific left/right response to the original curvature pattern. Five reversed-direction trials from different track positions all failed within ~50–60 steps, confirmed as a real, reproducible break rather than noise.

Mistake

"The math is symmetric" is not the same claim as "an already-trained fixed-weight network generalizes to the mirrored version of what it saw." It doesn't, automatically.

Fix

None applied yet within this lineage — noted as a retraining requirement, not a code bug. The clockwise convention was carried forward into the two-car racing work below, trained fresh from the start.

Physical safety net

Three ways a car can quietly go wrong

Beyond drifting off-track, live deployment surfaced two more failure modes the original single-env recovery logic never had to handle: tipping/rolling under sustained throttle, and the chassis settling at the wrong height without necessarily drifting laterally. Extended the recovery check to also trigger on the car's up-vector tilting past a threshold, and on its height deviating from the expected chassis height — plus a periodic "no real progress in the last few seconds" check, since a policy weaving in place near its start point trips none of the physical checks but still isn't racing.

06 Two-car self-play racing

The next expansion: both cars racing each other, both RL-driven, sharing a single policy network so that every car's experience — whichever physical slot it's driving — trains the same weights. A genuinely different problem from solo lane-following: the observation now has to describe another agent, and the reward has to survive two cars sharing the same road without collapsing into either constant collisions or overly cautious non-racing.

Architecture

Racing pairs, not clones

Same one-process, many-clones pattern as §5, but each clone now hosts a pair of cars sharing one track rather than a single car. Observation grew to 10 dimensions: the 7-dimensional curvature-aware state plus three opponent-relative features — progress gap, lateral gap, and relative speed, each computed so the two cars in a pair see exactly opposite-signed values of each other (verified antisymmetric in a smoke test before any training). A pair resets together, as one race, whenever either car's episode ends, so the opponent-relative features are never computed against a car that just silently teleported mid-race.

The collision penalty, first attempt

Punishing racing itself, not just crashing

Added a penalty when the two cars in a pair came within 1.8m of each other, applied every physics step they stayed that close — intended to discourage collisions. First full run showed a declining full-length rate across the run (79%→44% by quartile) and worst-case rewards spiraling from bad to catastrophic (-1152 → -2569).

Mistake

1.8m is normal separation during a legitimate overtake on a 9m-wide track, not a crash — and the penalty (5.0) was roughly 15–50× larger than every other per-step reward term, applied continuously for as long as the cars stayed close rather than once per contact. Any sustained close racing — the interesting part — collapsed the reward regardless of whether the cars ever actually touched.

Fix

Reduced the penalty to 0.4, tightened the trigger distance to 1.2m (closer to actual contact). Both pathologies disappeared immediately on the next run: full-length rate stabilized (no more quarter-over-quarter decline), worst-case reward stopped spiraling, and peak reward more than doubled in the same run (43.8 → 93.95).

Training progression

A slow, steady grind

Across several rounds on the corrected reward (roughly 900k cumulative steps for this lineage), peak reward climbed 93.95 → 100.03 → 106.1, and the full-length rate settled into a tighter, more stable band (42–49%) rather than swinging wildly quarter to quarter. Average reward stayed negative throughout — the same shape the single-env lineage went through before its final consolidating rounds, not a plateau.

"Car B seems to be winning"

Checking a claim the policy itself can't explain

Since both cars run the identical shared network on symmetric, verified-antisymmetric observations, there's no mechanism by which the policy itself favors one physical car over the other. The likely explanation lay outside the network: the demo stage's two cars spawn at fixed authored coordinates rather than the paired, centerline-computed positions training actually resets to, so one starting spot could plausibly be "easier" than the other purely as spawn luck — compounded by the policy still being only ~45% converged, where any single short demo run carries real random variance in which car happens to look better.

Removing the safety net

What the raw, unassisted policy actually does

At the user's request, removed the demo's recovery/reset logic entirely — no more teleporting a car back after it drifts off-track or tips over. This immediately surfaced a failure mode the recovery net had been silently masking every time it fired.

The chassis-collapse bug — unresolved

Five fixes, zero effect

Without recovery, both cars reliably ended up stuck: chassis settled at exactly half its own box height (0.2m, precisely CHASSIS_SIZE.z / 2) with a level, non-tilted orientation — consistent with the wheels no longer supporting the body at all, rather than a simple tip-over. Reproduced this via a scripted sustained-throttle stress test (no policy involved, ruling out "bad driving decisions" as the cause) and systematically tried five different fixes: higher PhysX solver iteration counts, an order-of-magnitude lower drive force, a heavier knuckle link, explicit chassis-vs-wheel collision filtering, and a much lower commanded wheel speed.

Mistake

None of the five changed the outcome even slightly — same collapse, same resting height, same rough timing, every time. That degree of consistency across five unrelated parameters is itself informative: it rules out a tuning-sensitivity problem and points at something more structurally wrong with this stage's joint setup, likely something specific to the hand-authored ground/physics-scene configuration (versus the original single-car stage, which used Isaac Sim's own default ground-plane helper) that hasn't been isolated yet. Collision between the two cars was also ruled out as the trigger — an earlier single-car test with two cars deliberately spawned far apart from each other showed the identical collapse with no possibility of contact.

Decision

Reinstated the recovery net as a documented, practical workaround rather than continue open-ended debugging — a collapsed chassis has no physical way to recover regardless of how good the driving policy is, so no amount of further training fixes this specific failure. The root cause remains open; the next diagnostic step, if picked back up, would be comparing this stage's ground/physics-scene setup line-by-line against the original working single-car stage rather than continuing to guess at car-side parameters.

07 Where it stands

  • Accepted baseline — pure RL, single car: car2_ppo_model.zip, 450k cumulative steps, reward settled around 105–113, full-length episodes the overwhelming majority. Still the most reliable, fully-converged policy in the project. The behavioral-cloning warm-start (§3) and a reversed-direction retraining attempt (§5) were both explored and did not replace it.
  • Experimental — parallel + curvature look-ahead, single car: car2_vec_ppo_model.zip, 470k cumulative steps, 7-dim observation. Higher peak reward (121.9) than the baseline but lower consistency (~50–60% full-length vs ~99%) — a genuinely different, not-yet-fully-converged lineage rather than a strict improvement.
  • Experimental — two-car self-play racing: car_race_ppo_model.zip, ~900k cumulative steps, 10-dim observation, one shared policy driving both cars. Peak reward climbing steadily (93.95→106.1 across the corrected-reward runs) but not yet fully converged (~45% full-length rate). Live-demo deployment requires the recovery net due to the unresolved chassis-collapse bug in §6.
  • Stuck-patch question (single-car lineage), resolved by observation: the ~140-second stuck patch seen once with the 150k-step policy did not recur in a full live demo of the 350k-step Run 6 policy — consistent with it having been a symptom of an under-trained policy rather than a standing recovery-logic bug.
  • Open issue: the chassis-collapse bug in §6 — reproducible, unresolved after five fix attempts, currently worked around rather than fixed.
  • Repo: a git repository has been prepared for this project (.gitignore excludes run logs, the Isaac Lab clone, and stray files) — organized commits are staged and ready, pending a decision on the author identity to commit under before this gets posted publicly.
